## 2. PayOnce PDF 目前具备哪些功能

> ⚠️ **本节及 §3–§8 是 2026-11-16 首轮 PainRadar 分析时的历史基线快照**（当时只有 F1–F9 / 7 个 UI 入口）。
> 后续两轮范围变更已覆盖这里的「功能缺失」结论：**见 §10（F10–F14）与 §11（F15/F16 + 网络口径修正）**。保留原样是为了保留当时的证据链，不要按本节对外描述现状。

### 2.1 功能清单（PRD §5 / CONTRACT §3，按当时真实状态）

| 编号 | 功能 | 代码状态 | 本机实测 | 限制 / 待测 |
|---|---|---|---|---|
| F1 | 合并 PDF（qpdf，已知密码、书签开关） | 已实现 | 验收 smoke 真实 qpdf 合并 `101 = 100 + 1` 页 | **不能合并各源文件的书签**（qpdf 重建文档树），已如实写入代码与文档；100 文件 ≤60s 待测 |
| F2 | 拆分（每 N 页 / 页码范围 / 书签层级） | 已实现 | 500 页按每 10 页拆出 50 份、合计 500 页 | 书签层级模式依赖 /Outlines，读不到则报错；真机待测 |
| F3 | 压缩到目标大小（lopdf 重编码图像 + JPEG 质量二分） | 已实现 | 仅编译与 schema 校验 | 20MB→≤5MB、文字层与书签保留、画质均待测 |

### 2.2 工程与交付层

- **UI**：§16 四区布局齐全；25 个前端文件 3786 行；浏览器预览模式为 mock 并常驻横幅；UI 交互冒烟 **11 PASS / 0 FAIL**（`tests/ui-interaction-smoke.mjs`）。

- **未完成**：macOS 构建与公证、Authenticode/EV 签名、CI secrets、生产更新端点、真机端到端测试。**当前安装包不可对外分发**。

> 状态总览见 `README.md` 里程碑表：M0 完成（Windows 本机），M1–M6、M8 为「代码与文档层落地」，M7 仅完成未签名 Windows 包。

## 4. 突出特点与优势：哪些是真的，哪些只是自我感觉

### 4.1 真优势（相对「订阅 + 云端」竞品）

1. **收费方式直击第一大痛点**：37% 的抱怨是「免费试用被立即扣费」。买断 + 不绑卡试用 + 7 天退款 + 明确 12 个月更新边界，是对该痛点的结构性解决；Adobe 官方条款与社区投诉提供了外部佐证。
2. **不上传且给出可验证方法**：`site/verify.html` 教用户抓包、断网测试、列出当时的两类网络请求（**现为三类，见 §11.3**）。竞品的隐私多为「承诺删除」，用户无法自行验证。
3. **无账号、无广告、无遥测、日志默认关闭**：直接对应 8% 的「广告多且强制登录」。
4. **失败不损坏原文件 + 批量可审计报告**：临时文件 rename、E1007、单文件失败不中断、`report.csv` 带错误码，面向批处理工作流；竞品多给结果、少给结构化失败台账。

### 4.2 被抵消的「伪优势」

| 宣称 | 实际 |
|---|---|
| 「不订阅」 | PDFgear / PDF24 / Stirling / PDFsam 完全免费，买断并不比免费便宜 |
| 「本地处理」 | 上述四款同样本地；PDFgear 仅 AI 旁路上传，PDF24 仅网页版上传 |
| 「功能够用」 | PDFgear 免费提供 PayOnce PDF 明确不做的 Word/Excel、文字编辑、批注、30+ 语言 OCR 与移动端 |
| 「一次买断」 | Foxit 有永久授权、PDF Expert 有 lifetime |
| 「不上传 = 隐私」 | PayOnce PDF **并非开源**，用户只能抓包验证网络行为，不能审计源码；Stirling PDF 在这一点更强 |

### 4.3 相对劣势

- 功能面明显更窄（§19 主动放弃深度编辑 / 移动端 / AI 等；Word/Excel 在 §5.2 列为 v1.1+；**批注并未被 §19 明确排除，而是 §5.1 功能表遗漏**——详见 §9 口径修正）。
- 效果与性能**全部待测**：OCR 准确率、压缩画质、300DPI 渲染、200 文件批量、签名兼容性。
- 当前无法交付：安装包未签名、macOS 未构建/未公证，用户装不上或被 Gatekeeper 拦截。
- 几乎全英文语料 → ¥169 国内定价与渠道无本地证据。

> **窄定位判断**：PayOnce PDF 真正可守的不是「便宜」或「离线」，而是「**对收费透明度与文件不出本机有硬性要求、且愿意为可验证的承诺付一次钱**」的桌面用户（PRD §2.2 的律师 / 会计 / HR）。这个人群存在，但规模未被 PainRadar 语料直接证明。

## 5. 痛点—功能逐条匹配（PainRadar 九大需求）

| # | 痛点（原文锚定） | 证据 / 占比 | 机会分 | PayOnce PDF 对策 | 判定 |
|---|---|---|---|---|---|
| 1 | 免费试用被立即扣费 | 123 / **37%** | 48 | 买断 + 不绑卡 7 天试用 + 7 天退款 + 12 个月边界写清 | **直接解决（商业模式层）**；付费意愿尚未验证 |
| 2 | 格式转换收费且失败 | 28 / 8% | 34 | F4 仅 PDF⇄PNG/JPG；本地处理避免上传大小限制；错误码 + 不覆盖原文件 | **部分解决**：Word/Excel 明确不做；原文里有「$70/年 converter 仍提示 too big」类场景，本地大文件能力待测 |
| 3 | 广告多且强制登录授权 | 27 / 8% | 28 | 无账号、无广告、无遥测 | **直接解决** |
| 4 | 签名表单流程走不通 | 25 / 8% | 33 | F6 签名图片叠加 + 字段 /V + 扁平化开关 | **代码层解决、效果未验证**；外观流有限，Adobe Reader 打开待测；原文「付 $99/年仍只让寄 5 份」属配额痛点，买断可规避 |
| 5 | 编辑后文件损坏或丢失 | 22 / 7% | 29（LLM 簇 opp 63.5，最高之一） | 临时文件 rename、不覆盖输入、E1007、取消不改原文件 | **部分解决/回避**：能保证「不被工具弄坏」，但**不做深度编辑**，用户想改文字的需求本身未解决 |
| 6 | 批注高亮操作难且易丢 | 6 / 2% | 28 | 无 | **不解决**（§5.1 未列入；PRD §2.2 persona 却写了律师「批注、脱敏」，属范围遗漏而非明确非目标） |
| 7 | OCR 差且速度慢 | 7 / 2% | 27 | F5 本地 Tesseract eng/chi_sim，输出可搜索 PDF/TXT | **未验证，可能不解决**：原文抱怨正是「older typeset books 识别差，只好改用 Claude」，本地 Tesseract 在复杂版式上通常弱于云端 |
| 8 | 文件管理混乱难定位 | 6 / 2% | 24 | 文件列表排序/删除 + 批量 `report.csv` | **部分缓解**，但不是文件管理器 |
| 9 | 打印与邮件导出失败 | 4 / 1% | 22 | 无（仅「打开输出文件夹」） | **不解决** |

**覆盖度统计**：

- 商业模式类痛点（1、3，约 45%，加上 2 的收费部分则超过一半）→ 结构性解决，这是产品最锋利的地方。
- 功能类痛点（2、4、5、7、8、9）→ 2 项部分解决、1 项代码完成但待测、1 项回避、1 项部分缓解、2 项明确不做。
- LLM 台账里机会分最高的「**编辑文字与图片**」(opp 63.5, 22 条) 恰好是 PRD §19 主动放弃的功能——**最大的功能机会被有意让给了免费竞品**。

- Adobe 官方订阅条款（2026-08-01 生效）：免费试用结束自动按购买费率扣款；年付合同 14 天后取消，一次性收取剩余合同金额 50%。
- Adobe 官方帮助页：试用期结束未取消即自动扣费；14 天后不退款。
- Adobe 社区 2026-06-30 真实投诉：「点了免费试用就被扣 478.80 TL，想取消又被要求付 2,633.40 TL 提前解约费」。
- PainRadar 原文锚定证据：「*Your company just charged me $15.17 for selecting your 7 day free trial*」。

## 6. 结论：这些特点能解决用户困难吗

**能解决的**：用户最集中、最情绪化的困难——「不想再被订阅、试用扣费、强制登录和广告折腾」。这是真实且被 723 条评论 + 官方条款双重佐证的痛点，PayOnce PDF 的商业模式设计正面对准它，而且没有竞品在「收费透明度 + 可验证不上传 + 无账号」这三点上同时做到同等强度。

**解决不了的**：PDF 使用过程中的**功能性**困难。想改文字、想批注高亮、要 Word/Excel、要打印/邮件、要移动端、要复杂版式 OCR——这些恰是 PainRadar 里机会分不低、且免费竞品已经免费提供的部分。按当前范围，PayOnce PDF 对约 27% 的功能类抱怨只能覆盖一小半。

**还不能下结论的**：以上「能解决」目前只成立在**设计与代码层**。产品尚未在真机跑通端到端、安装包未签名、macOS 未公证、OCR/压缩/签名效果全部待测、7 天预购验证没有执行。因此更准确的说法是：**产品定位对准了最大的痛点，但还没有任何一个真实用户用它解决过问题。**

## 9. 补记：「改文字为什么没做」的可行性复核（2026-11-16）

> 触发：用户以个人经验指出「改文字最重要」，并质疑「免费竞品 PDFgear 能提供，为什么我们办不到」。
> **结论先行：不是技术不可行，也不是 §9.2 许可红线阻挡，而是 PRD 的范围决策与成本结构。**
> 前一轮口头说明把「技术代价高 / AGPL 禁令」列为理由，属于论证错误，在此更正。

### 9.1 实证：能改文字的引擎已经在安装包里

| 事实 | 证据 |
|---|---|
| PDFium 已随包且合规 | `src-tauri/Cargo.toml` 有 `pdfium-render = "0.9"`；`src-tauri/resources/pdfium.dll` 7.5MB，**BSD-3**，在 §9.2 白名单内 |
| 绑定已提供完整文本编辑 API | 本地 `.toolchain/cargo/registry/.../pdfium-render-0.9.5/src/pdf/document/page/`：`PdfPage::text()`、`PdfPageText::search()` / `chars_for_object()`、`PdfPageTextChar::unicode_value()` / `tight_bounds()` / `font_name()`、`PdfPageTextObject::set_text()`（底层 `FPDFText_SetText`）；`pdf/document.rs::save_to_file()` |
| 我们只用了渲染 | `src-tauri/src/engine/render.rs` 只调 `page.render()` 输出位图；全项目 grep 不到任何文本提取或文本对象写入 |
| 我们甚至已经能「写」文字 | `src-tauri/src/engine/pdf.rs::bake_text_appearance()` 往 content stream 写 `BT /FOnce ... Tj ET`；但用 Helvetica/WinAnsi，非 ASCII 降级为 `?`（中文写不进） |

也就是说，「定位文本对象 → 读原字 → 替换 → 写回 PDF」这条链路的**底层能力已随包提供**，缺的是调用它的业务层与交互 UI，不是新引擎、新依赖或新授权。

### 9.2 约束复核：哪些是真的，哪些是自设的

| 约束 | 判定 |
|---|---|
| §9.2 禁 MuPDF / Ghostscript（AGPL） | **不挡改文字**。它挡的是 Word/Excel 所需的版式重建后端；文本编辑走已在包内的 PDFium |
| §8 安装包 ≤100MB | **不挡**。当前包 27MB，PDFium 7.5MB 已计入 |
| §6 本地优先 / 不上传 | **不挡**。编辑纯本地 |
| §19 第 3 条「不做深度排版编辑」、§5.2 页面编辑列 v1.1+、§4「不做全能」、§21「不是更好的 PDF 编辑器」 | **真障碍，且是白纸黑字的产品决策**（PRD 前言亦写「第 19 节是非目标，越界的功能一律不做」） |
| §15 六周排期、每里程碑须交双平台安装包 | **真障碍**（资源） |
| §18「支持邮件 ≤0.1 封/单」、无客服团队、$19 一次买断 | **真障碍（成本结构）**。编辑是个案差异最大的功能：字体子集、CID、中文、竖排、表格、扫描件，每个失败都是支持邮件 + 退款；§17 已把「质量差 → 口碑」列为风险，§6 要求「做不到的写进 FAQ，不夸大」 |

### 9.3 PDFgear 为什么能提供（2026-11-16 公开检索，需复核）

- 官方《Statement on the Organised Spread of Disinformation》自述：「*As a startup, we use well-established SDKs that are widely adopted in the PDF industry. This approach allows us to focus on improving the overall user experience rather than rebuilding common technical foundations from scratch.*」→ **集成成熟 PDF SDK，不自建编辑引擎**。
- PDF Gear Tech Pte. Ltd.（新加坡，2022 起），投资驱动、口碑获客、官方承认「free for now」（未来拟对 AI / 高精度 OCR / 复杂转换收费）；**编辑是核心获客钩子**，有跨平台团队与 4 年迭代。
- 但它交付的是「通常能用」，不是万能：仅改**可选中文本**；扫描件需先 OCR 或**叠加文本框（overlay，并非改原文字）**；官网自承「*works best for short text replacements*」、缺字体需手动安装、长替换影响换行；CNET 2026 评测列「*No layout reconstruction*」；复杂表格 / 多栏易乱、>100 页变慢、部分 AI 与高级转换走服务端上传。
- 它敢给「usually」，是因为**免费、用户预期低、不承担付费后的客服与退款成本**；PayOnce PDF 收 $19 且定 0.1 封/单，容忍度完全不同。

### 9.4 这与 §1.4 假设相冲突

PainRadar：`edit` 67 条评论 / 23 个痛点原子；LLM 台账「编辑文字与图片」机会分 **63.5（全表最高之一）**；「编辑后文件损坏/丢失」22 条 7%。
用户经验、语料方向、竞品把编辑当主钩子，三者同向，与 §1.4「用户更在意收费方式，而非功能多少」相悖，而 `preorder.md` 要求「写代码之前」跑的 7 天预购验证被跳过。
样本 = 1 不足以下市场结论，且 547/723 语料来自移动 App 评论，桌面付费人群的功能权重仍需补证据；但足以要求重验假设。

### 9.5 可选路径（工期为估算，非承诺）

| 层级 | 内容 | 代价 / 风险 |
|---|---|---|
| L0 覆盖式 | 白底遮盖 + 叠加新文字；`bake_text_appearance` 原语已在 | 数天。中文写不进、复制出来仍是旧字、非真改文本层；**§6 诚实原则下不得冒充「改文字」**（PDFgear 对扫描件用的正是这类降级） |
| L1 真改文本层 | 窄功能「查找并替换文字」：现有 `search()` + `chars_for_object()` + `set_text()` + `save_to_file()`，加一个命令、参数面板与预览 | 约 1–3 周。难点是嵌入字体子集（中文新字形写不进）、行宽溢出、复杂版式；需放宽 §19/§5.2，把 §21 定位从「工具箱」改为「轻量编辑器」，同步改官网「不支持清单」 |
| L2 所见即所得编辑器 | 选区 / 光标 / 撤销 / 段落回流 / 对象拖拽 | 按月计 + 长期维护，与六周排期和 $19 成本结构不兼容 |

**前置**：先跑 `preorder.md` 的 7 天验证，落地页 A/B——A「不改字，但绝不被扣费」 vs B「能改字，一次买断」。B 胜出则 L1 值得做；A 胜出则维持范围，但必须正面回答「$19 凭什么 vs 免费 PDFgear」。

### 9.6 真实场景锚点：就地改几个字（2026-11-16 用户原话）

> 「在 Acrobat Reader 中编辑功能是要收费的，我往往因为这而苦恼，因为，我有时看一份 PDF 文档，发现里面有些地方需要修一下，只能有两种选择：一是将它转换成 word 后进行修改，修改后再转回 PDF；二是直接在原 PDF 文档上修改。我更喜欢后者的方式。」

**Adobe 官方口径（2026-11-16 核实）**

| 来源 | 原文 |
|---|---|
| `adobe.com/acrobat/pdf-reader.html` FAQ | 「*Text and image editing is not available in Acrobat Reader and requires an Adobe Acrobat Standard or Adobe Acrobat Pro subscription.*」免费 Reader 仅 view / print / annotate / fill & sign |
| Adobe 中文 Reader FAQ | 「您無法使用 Acrobat Reader 對 PDF 文件中的文本或圖像進行**永久更改**。要編輯 PDF 文件，請購買 Adobe Acrobat 軟件。」 |
| `helpx.adobe.com/hk_zh/reader/using/open-edit-or-delete-pdfs` | 「編輯文字」「合併 PDF」「建立表格」均列為需 Acrobat 的進階編輯功能 |
| Adobe Reader FAQ（导出） | 「導出 PDF」轉 Word / Excel 同樣需訂閱 **Export PDF**；Reader 的「直接在頁面上鍵入文本」是**自由文本注释**，不是改原文字 |

→ 用户描述的两条路径在 Adobe 生态内**都落在付费墙后**。这不是偶发体验，是结构性门槛；且比「试用被扣费」更日常、更高频、更刚性。

**这个场景暴露的 PRD 问题**

1. **§19 把两件不同的事绑成一个词**：「不做 PDF 深度排版编辑（**改文字、重排**）」。用户要的恰恰是**不重排的就地替换**（§9.5 的 L1），却被「深度排版 / 重排」（L2）连坐禁止；§5.2「页面编辑（改文字、换图）」同样整体打包推到 v1.1+，未拆出窄功能。**属于范围定义过粗造成的误伤，不是论证过的取舍。**
2. **§17 的推论方向反了**：PRD 因「PDF→Word 质量差」得出「v1 不做，明确写不支持」；但用户抱怨的正是**被迫绕 Word**（两次转换 + 版式风险 + 需要 Word）。正确推论应是「直接改字，让用户完全跳过转换」，而不是「连改字也不给」。
3. **与产品定位高度自洽**：「不订阅 + 本地 + 一次买断」正面命中「Reader 改字要订阅」。比 §1.4 主打的「试用扣费」更贴近日常使用，且是低频轻量、单文件、可明确报错的场景。
4. **§9.2 的「客服成本」反对此场景不成立**：那是对 L2 全功能编辑器而言。窄功能边界可枚举（只改可选中文本；字体子集 / CID / 嵌入字形不支持时**返回明确错误而非乱码**），失败可预期，符合 §4「做不好的明确说不支持」与 §18「支持邮件 ≤0.1 封/单」。

**建议的 F10「就地替换文字」边界（待用户确认，尚未实现）**

- **In scope**：可选中文本的查找 / 替换，保持原字体、字号与坐标；不重排、不回流；单文件或页范围；输出新文件、不改原件。
- **Out of scope**：扫描件（提示先走 F5 OCR，且不保证）、中文 / 新字形写入（字体子集不支持时返回明确错误码）、复杂表格与多栏、图像与对象编辑、所见即所得光标编辑。
- **验收**：替换后文本层可复制出正确文字；页数与页面尺寸不变；Adobe Reader 打开无损坏（真机待测）。
- **需同步修改**：PRD §19 / §5.2 / §5.1、`CONTRACT.md` 命令表与错误码、`site/index.html` + `index.zh.html` 的「不支持清单」、`site/faq.html`、`docs/user-manual.md`、`docs/test-report.md`。
- **预购 A/B 的 B 版文案可直接用用户原话**：「看 PDF 时发现几个字要改？不用转 Word，不用订 Acrobat。就地改，一次买断。」

**诚实边界**：这个诉求已被**免费的 PDFgear 桌面版**零成本满足（本地、无需注册、Edit → Edit Text）。因此 $19 不能只靠「能改字」成立，仍需 §1.4 假设被验证；对只想就地改几个字的用户，最优解是现在就用免费工具，而不是等 PayOnce PDF。

### 10.2 事实前提被纠正（对定位影响很大）

用户判断「PDFgear 也是本地处理，并没有另调云上 API」——核心功能属实，但不完整。PDFgear 官方 2026-03-24 声明自承：

- 「*Advanced features such as AI and certain tasks on mobile apps still use secure server-side processing*」；
- 官方另设专节解释「*Why does PDFgear utilise server-side processing for compression and conversion?*」，称正在转向本地；
- 隐私政策经第三方核对：AI 走 **Microsoft Azure OpenAI Service**，用户显式同意后传输 PDF 内容与对话文本；
- 「*In the future, we may add a few paid options for advanced tools, such as AI-powered features, high-accuracy OCR, and complex PDF conversions*」。

→ 「文件内容永不上传」「收费确定性」不是双方相同的前提，而是**我方可以超过它**的维度。为对标而加云端 AI，反而会丢掉最锋利的差异点。（§11.3 补充：F16 语言包下载后，「零云调用/零网络请求」的绝对表述不再成立，正确承诺是「文件永不上传 + 三类请求可枚举」。）

### 10.3 仍未解决的矛盾

1. **功能对标 vs 成本结构**：$19 买断、支持邮件 ≤0.1 封/单、六周排期，与编辑器的高投诉密度冲突。需用户在「提价 / 严格收窄边界 / 开源核心 + 社区支持」中择一（PRD §22.6）。
2. **三项结构性落后**：高保真 Word/Excel/PPT（需商业 SDK 或 ~200MB LibreOffice）、AI 问答（必须云端或本地大模型）、移动端/网页版。按字面「不能比它弱」这些仍需补，但都有硬约束。
3. **验证缺口**：新功能只有编译 + 11 项单测（含 2 项真实 PDF 文件级）+ OOXML 被 Python `zipfile`/XML 解析验证；**真机 Tauri 端到端、CJK 字体替换、注解在 Adobe Reader 显示、AES-256 实测全部未做**。不能宣称「已对标成功」。
4. §1.4 的三个可证伪假设、`preorder.md` 的 7 天验证**依然未验证**；功能补齐不改变这一条。

### 11.1 §10「仍缺的功能」中已被本轮补齐的部分

| §10.1 旧状态 | 第二轮新状态 |
|---|---|
| 「表单创建、脱敏、打印/邮件仍缺」 | **F15/F16 已落地**：AcroForm 文本域、真脱敏（真删文字对象）、顶层书签、系统打印、mailto 邮件、TXT/CSV/HTML → PDF、中文水印、42 种 OCR 可选语言包。前端由 12 入口扩到 **15 个** |

**新增的诚实边界**（不能写成「已全面对标」）：表单只有文本域（无复选框/单选/下拉）、书签只有顶层且页面增删不跟随页号、中文水印是水平居中灰字（无旋转/独立透明度）、打印无应用内预览、mailto 附件需手动添加、文本转 PDF 只做纯文本排版、HTML 只剥标签不渲染 CSS。

### 11.2 验证层级从「编译通过」升级到「真实 PDF 文件级」——这是本轮最大收获

第一轮把 F10 写成「已实现」，依据是 `cargo check` + 纯逻辑单测。第二轮把 `JobCtx.app` 解耦为 `Option<&AppHandle>`、把 PDFium 注入引擎函数后，写了 **28 项 Rust 单测，其中 11 项用真实 PDF 文件 + 真实 PDFium DLL + `qpdf --check`**，实证抓出两个「假成功」：

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | **F10 改字返回成功，但重新打开 PDF 文字仍是原文**；中文缺字形保护也没触发 | PDFium 规定保存前必须 `FPDFPage_GenerateContent`，否则对象级修改全部丢失；`FPDFText_SetText` 对字体缺字形字符会**静默写空格**而不报错 | 每页 `page.regenerate_content()`；非 ASCII 替换前检查 `font.is_built_in()` / `is_embedded()`；**写后读回校验** `verify_edit()`，读不到新文字就删除输出并报错 |
| 2 | 旋转 90° 后 F11 找不到文字、F14 导出空白 | 随包 PDFium 在 `/Rotate ≠ 0` 页面 `FPDFText_*` 返回空文本（内容流与字体资源完好） | `with_unrotated()`：查找/提取时生成只把 `/Rotate` 置 0 的临时副本，正式输出保留原旋转；改字校验改用文本对象拼接 |

> 方法论结论（对 §7「待验证问题清单」的修正）：**编译通过 + 纯逻辑单测不构成「功能可用」的证据**。凡涉及 PDF 二进制产物的能力，必须有「重新打开产物并读回断言」的文件级测试。§10.3 第 3 条「只有编译 + 11 项单测」的验证缺口描述已被本节部分填补，但**真机 Tauri GUI 端到端、Adobe Reader / Word / Excel 打开产物、AES-256 阅读器实测依然未做**。

### 11.3 「零云调用」口径必须修正（影响 §4.2 / §10.2 的定位表述）

F16 引入了全产品**唯一**的运行时联网点：用户主动点击「安装 OCR 语言包」时，用包内 `ureq` 下载 `https://raw.githubusercontent.com/tesseract-ocr/tessdata_fast/main/<lang>.traineddata`。三条硬约束：只由用户主动触发、URL 只含语言代码、下载的是公开静态字典且不调用云端处理/AI 接口。

因此「**零网络请求**」「**任何功能都不联网**」不再严格成立，继续这么写会在抓包验证时被用户当场证伪。正确承诺改为：

> **文件内容与文件名永不上传；任何文件处理功能都不联网；运行时网络请求只有三类且可枚举、可抓包验证。**

三类：① 一次性激活（密钥 + 不可逆机器指纹哈希）；② 可选更新检查（版本/平台/架构，可关闭）；③ 用户主动安装 OCR 语言包。

**这个修正不削弱 §10.2 的竞争判断**：PDFgear 官方承认其 AI 把 **PDF 文件内容**发往 Microsoft Azure OpenAI，我们下载的是不含任何用户数据的公开字典，两者性质完全不同。「文件内容不上传」仍是我方可防守的硬承诺，只是表达必须精确。

### 11.4 仍未解决（与 §10.3 相同的结构性矛盾）

1. **功能面对标仍有硬缺口**：WYSIWYG 编辑器、图片/形状/链接/文本框编辑、图章绘图、复选框/单选/下拉表单域、应用内打印预览、邮件自动附附件、网页版、macOS 构建与签名。按用户「只能比它强不能比它弱」的字面要求，这些需单独立项。
2. **真机验证与分发**：Tauri GUI 端到端、阅读器兼容性、Windows Authenticode / macOS 公证、双平台安装包全部未完成，安装包**不可对外分发**。
3. **定价与成本结构**：定价挂起已于 2026-11-16 解除（见 §12 / PRD §22.8，$29 / ¥169，提价 + 收窄边界同时执行，不开源）；但 **§1.4 三假设与 `preorder.md` 预购 A/B 依然未验证**，定价拍板并不能替代商业验证。功能补齐不改变这一缺口。
