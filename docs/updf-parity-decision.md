## 0. 「对标」的定义（最重要，先划边界）

UPDF 3.0 是「桌面 + 移动 + 云 + AI」的整条产品线。若把「对标」理解成逐项复刻，需要商业转换 SDK、云端账号体系、移动端团队与多年迭代，与本项目「单人 + AI 代理、6 周排期、27 MiB 离线包、一次买断」的硬约束直接冲突。

**因此拍板：对标范围 = 桌面端、离线、PDF 文档工作台能力。**

| 层 | 定义 | 处理 |
|---|---|---|
| **L1 本轮交付** | 产品形态与可安装性：内置文档视图、页面与工具联动、OCR 打包缺陷、授权设备口径、工作台视觉 | **本轮改代码并重建安装包** |
| **L2 排期（单独立项）** | 功能宽度补齐：批注类型、表单域、文档对比、PDF/A、Bates、测量、应用内打印预览、预览上框选批注 | 给出清单与依赖，**本轮不做，不谎称完成**；2026-11-20 后续：首项「预览框选」已提前以 **F18 定位闭环 v1** 交付（PRD §22.12），其余条目仍未做 |
| **L3 明确不做** | 上云能力：云端 AI 问答/摘要/翻译、账号体系、云同步、Web 端、eSign 邀请签署与状态跟踪、跨设备接力 | 按用户「上云不要学」**排除**，并转化为隐私卖点 |
| **L3' 许可/体积硬约束** | WYSIWYG 深度排版（段落回流、对象拖拽）、高保真 Word/Excel/PPT 转换 | 需商业 SDK 或 ~200 MB LibreOffice，撞 PRD §8 体积上限与单档价格；**保持 F10 就地替换文字 + 不重排**，官网明示 |
| **L3'' 移动端** | iOS / Android | **不是「移动端必然上云」，但也不是纯排期问题**：核心 PDF 处理可完全离线；真正阻塞的是 sidecar 子进程架构、三套 native 二进制、沙盒/交互重写、以及**商店内购收据与离线证书授权模型的冲突（会引入新的云依赖）**；双平台桌面尚未签名公证，先把桌面做实。详见 §5 补正 |

> 诚实边界：UPDF 的核心编辑/转换/OCR 也是本地离线，只有 AI/eSign/云同步上云。所以 L3 排除的是「上云部分」，不是「把本地处理当成差异化」。

## 1. 价格拍板

**UPDF 参照**：买断 $84.99（黑五，原价 $139.99）/ ¥238 终身；年订阅 $54.99 / ¥128；**AI 另收 $69/年或 ¥148–238/年**；一个账号 4 台设备。

**拍板：$39 / ¥199 一次买断；首发 14 天早鸟 $29 / ¥149；单档不变。**

| 项 | 决定 |
|---|---|
| 正式价 | **$39 / ¥199**（原 $29 / ¥169，**上调**） |
| 早鸟 | **$29 / ¥149**（原 $19 / ¥109，首发 14 天，折扣码，非常设价） |
| 档位 | 单档；不设 $10 入门档、不设团队/席位档、**不设 AI 加购** |
| 授权设备 | **一把钥匙最多 3 台设备**（原「一机一密钥」）；服务端按密钥记录不同机器指纹，仍是各自离线缓存、无账号 |
| 更新/试用/退款 | 全部不变：12 个月 1.x 更新、7 天全功能试用不绑卡不留邮箱、7 天无理由退款、2.x 老用户五折 |

**为什么涨到 $39 而不是维持 $29**：
1. 功能范围从「15 个批量工具」扩到「文档工作台 + 阅读视图」，编辑类是投诉密度最高的功能，`pricing-decision.md` 的「支持 0.1 封/单」模型在 $29 下已经紧，$39 留出客服余量。
2. ¥199 vs UPDF ¥238 = **便宜 16%**，正好是用户说的「便宜一点」；$39 vs $84.99 = 便宜 54%，且对方还要每年 $69 的 AI 费，**总持有成本差距更大**。
3. 不回到 $10 级低价：原决策文档已论证参照系是 $0 与订阅陷阱，不是绝对价格；降价也赢不了免费。
4. **3 台设备**修补上一轮发现的硬伤：原「一机一密钥」让 4 台设备要 $116，反而贵过 UPDF 买断 $84.99。现在 3 台共 $39。

> 生产侧待办（人工）：Gumroad 商品价格与折扣码、激活服务按 key 计数的持久化、国内渠道 ¥199 展示、所有对外页面复核。本轮只改配置与文案，不改收银台。

## 3. 外观拍板

**原则：实用优先于装饰。** UPDF 的优点是「文档在中间、工具在两侧」；缺点（第三方评测）是功能多导致卡片堆叠、层级深。我们的做法：

1. **三栏工作台**：左 = 分组工具导航（图标 + 中文 + 一句提示，15 项，独立滚动）；中 = **文档画布**（页面渲染 + 翻页/缩放/页码）+ 文件队列；右 = 参数与操作卡片。
2. **浅 / 暗双主题**，跟随系统并可手动切换；暗色下文档画布用中性深灰，避免白纸刺眼。
3. **层级靠间距与留白**，不靠重边框；卡片圆角、柔和阴影、克制的过渡动效（≤180ms），不引入装饰性插画干扰文档阅读。
4. **状态永远可见**：任务进度、输出、错误码在底部固定条；预览模式横幅常驻且不可关闭。
5. **无障碍**：键盘可达、焦点环、对比度 ≥ 4.5:1、按钮有 aria-label。

> 诚实边界：「比 UPDF 漂亮」是主观判断，无法客观证明。可交付的是**可截图对比的具体设计**与「实用」上可量化的改进（选页即见、改字后可在同一窗口目视确认、参数不跨屏滚动）。

## 5. 补正：移动端与云依赖（2026-11-20 22:46，用户追问）

> 修正 §0 表格 L3'' 原写法「不是上云问题，是排期问题」。该表述过于绝对：**核心 PDF 处理不必上云，但移动端的分发与授权环节会引入新的云依赖**，与本项目「无账号 + 离线证书」口径存在真实张力。本节是补正，不改变 L3'' 的「继续暂缓」结论。

### 5.1 三层拆开看

| 层 | 是否必须联网 | 说明 |
|---|---|---|
| **核心处理层**：PDF 渲染、就地改字、批注、加解密、合并拆分、Tesseract OCR | **不必**，可完全离线 | 移动端 SoC 跑 PDFium / lopdf / Tesseract 可行（更慢、更耗电）。UPDF 的 OCR 是 1.4–1.68 GB 本地插件；PDFgear 核心编辑也是本地；Xodo / Foxit 均可离线 |
| **分发与授权层**：商店内购、收据验证、恢复购买、更新下发、崩溃/审核 | **必然触网** | App Store / Google Play 分发本身是云；Tauri 自动更新器在移动端不适用，更新走商店；数字功能受 StoreKit / Play Billing 规则约束 |
| **增值层**：云端 AI、账号、云同步、eSign 邀请跟踪、跨设备接力 | **必须上云** | 已按用户「上云不要学」排除，L3 明确不做 |

**PDF 处理放服务端不是技术必然，是商业取舍。** PDFgear 官方原话（已记于 `docs/pdfgear-parity-matrix.md:20`）：「*Advanced features such as AI and certain tasks on mobile apps still use secure server-side processing when high computing power or licensed SDKs are required*」——即部分移动端任务因算力/授权 SDK 被挪到服务端。若我方照做，会直接摧毁「**文件内容与文件名永不上传**」这条 PRD §22.7 红线，**这是做移动端时最需要守住的一条，不是最需要妥协的一条**。

### 5.2 真正阻塞的四项（都不是「会不会上云」）

1. **引擎架构：spawn 子进程在移动端不可用。** `engine/qpdf.rs` 与 `engine/ocr.rs` 用 `std::process::Command::new(bin)` 启动 `qpdf.exe` / `tesseract.exe`；`sidecar.rs` 按桌面路径定位 Windows DLL。Tauri 2 移动端（iOS WKWebView / Android WebView）**不允许任意启动子进程**，也没有桌面式 sidecar 部署。F1 合并/拆分/压缩与 F5 OCR 需改为静态链接库调用，不是换一个编译目标。
2. **二进制要换三套。** `src-tauri/resources/` 现有 84 MB 全是 Windows x64 DLL（`libicudt75.dll` 30 MB、`pdfium.dll` 7.5 MB、`qpdf29.dll` 7.3 MB、`libtesseract-5.dll` 3.2 MB 等）。移动端需 iOS arm64 / Android armv8 的 PDFium（社区 `pdfium-lib` 可编译，但要自建补丁链与版本维护）、Tesseract + Leptonica NDK 交叉编译、qpdf 替换或改用 `lopdf`。§8 的 ≤100 MB 体积约束在移动端同样吃紧。
3. **沙盒与交互要重写。** 移动端只能访问自身容器与用户经文档选择器选中的文件；批量文件队列、`report.csv` 落盘、「打开输出目录」、系统打印 / `mailto:`、多窗口 / 托盘 / 全局快捷键都要重做或砍掉；三栏工作台在 6 寸屏上不成立，需单独响应式设计。
4. **授权模型冲突（最硬的一处）。** 现为「机器指纹 + Ed25519 离线证书 + 一把钥匙最多 3 台设备」。移动端没有稳定机器指纹（IDFV / 广告 ID 会变、重装即变、受隐私限制），也不能让用户手输 `PAYONCE-XXXX-XXXX-XXXX`；商店规则要求数字功能走内购。可选路径只有两条：**① 商店非消耗型一次性买断 + 本地收据验签**（StoreKit 2 `VerificationResult` / Google Play 本地签名校验，可不建服务端，但要引入「恢复购买」与商店服务器依赖）；**② 自建账号体系做跨设备授权**（= 上云，且直接违反 PRD §19「无账号」）。本轮选继续暂缓。

### 5.3 若将来立项，建议路径

先让桌面真正发布（Authenticode / Developer ID + 公证、真机 60 条用例、F17 真实窗口渲染），再单独立项做**移动端离线伴侣 App**：只带渲染 + 批注 + 就地改字，静态链接 PDFium，不带 OCR 与批处理；授权走商店非消耗型买断 + 本地收据验签，不引入账号。这样能保住「文件永不上传」。但要明确：它是**另一个产品**，不是本项目的一个编译目标；Apple Developer 年费、双平台审核、每年 iOS/Android 大版本适配、商店 15–30% 抽成，都会冲击「一次买断 $39、无后续收入」的成本结构。

> 结论：**移动端 ≠ 必须调云端 API；但「做移动端且保持现有授权与隐私口径」不成立。**「不做移动端」的首要原因是引擎架构与授权模型，其次是桌面尚未发行就绪，上云是次要顾虑。
