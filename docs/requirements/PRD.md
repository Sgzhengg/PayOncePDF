## 1. 为什么做这个产品

### 1.1 数据事实

> **语料口径注（2026-11-20）**：本节基于 723 条评论 / 333 痛点原子的旧语料；定位 v2 改用 300 样本 / 81 条有效痛点的新语料（见 `docs/positioning-v2.md`）。两套分母不同，对外文案统一用新语料的 40% / 6% / 11%，本节 37% 仅作历史论证保留。
抓取 10 个主流 PDF 应用的 723 条近期评论（App Store + r/PDF），333 条含具体抱怨：

| 抱怨 | 占比 |
|---|---|
| 免费试用被立即扣费 | **37%** |
| 格式转换收费或失败 | 8% |
| 广告与强制登录 | 8% |
| 签名表单走不通 | 8% |
| 编辑后文件损坏 | 7% |
| OCR 差或慢 | 2% |

**一半以上的抱怨指向收费方式，而不是功能。** PDF 功能早已同质化，用户真正缺的是"不骗人收费、不上传文件"的工具。

### 1.2 战略：用成本结构打价格战

马斯克式打法的核心不是"卖得便宜"，而是**成本结构不同，所以能便宜**：

| 成本项 | 竞品 | PayOnce PDF |
|---|---|---|
| 云端 OCR/存储 | 持续支出 | 本地处理 ≈ 0 |
| 账号/风控/客服团队 | 有 | 无账号，邮件支持 |
| 销售团队 | 有 | 无 |
| 边际成本 | 随用量增长 | ≈ 0 |

因此可以做到：

- 竞品 Smallpdf ≈ $108/年 → PayOnce PDF **$39 买断**（约 1/4）；
- 竞品 Adobe ≈ $240/年 → PayOnce PDF **$39**（约 1/8）。

> **§1.2 补注（§22.8 定价决策）**：本节「成本结构不同，所以能便宜」的结论不变，但**低价是结果不是策略**：不能为了「更便宜」把价格压到 $10。定价由成本结构给出下限、由竞争格局给出上限，最终拍板 $29，依据见 `docs/pricing-decision.md`。

### 1.3 为什么能挖走存量用户

1. **痛点直接**：37% 的人在骂扣费，价格与收费方式是他们的第一决策因素；
2. **切换成本低**：PDF 工具没有数据锁定，下载即用；
3. **差异化清晰**：本地处理是律师/会计/HR 的硬需求，云端竞品做不到；
4. **传播自带话题**："我受够了订阅"是社区里最容易共鸣的叙事。

### 1.4 必须为真的三个假设（可证伪）

| 假设 | 验证方式 | 失败信号 |
|---|---|---|
| 用户更在意收费方式，而非功能多少 | 预购页转化率 | 访问够但定金 0 |
| 本地处理是购买理由 | 社区评论/访谈 | 用户说"我不在乎上传" |
| $39 买断能覆盖获客成本 | 自然流量占比 | 必须投广告才卖得动 |

## 2. 产品定位

> **一个不订阅、无广告弹窗、文件内容永不上传的本地 PDF 工具箱（15 个工具）。**

一句话（2026-11-20 定位 v2 修正版，见 `docs/positioning-v2.md`）：
*Buy once. Works offline. No subscription.* / *一次买断的 PDF 工具——本地处理、不订阅、无广告弹窗。*

- **主用途（2026-11-20 拍板，见 `docs/primary-use-case-decision.md`）**：桌面离线、一次买断的 **PDF 就地修订**——看 PDF 时发现错字，直接在原文件上改掉，不转 Word、不重排版、不订阅、不上传。阅读批注是形态层（不收费）、格式转换与 OCR 是辅助层（不主打）、深度排版与云端能力明确不做；对外首屏讲这条主线，15 个工具降为第二屏。
- 首屏限定：核心工具断网可用；仅首次激活、可选更新检查与用户主动安装 OCR 语言包会联网，文件内容与文件名永不上传。
- 授权本身不过期 ≠ 永久免费更新：含 12 个月 1.x 更新，2.x 老用户五折。
- 不宣称「没有免费替代」（免费桌面编辑器确实存在）；对外口径是「免费替代最弱、又被订阅伤害最深」，并以「功能不弱于免费竞品 + 文件永不出门」兜底。
- 数据统一采用 300 样本 / 81 条有效痛点（付费与订阅 40% / 3.8、弹窗广告 6% / 3.8、编辑与表单 11% / 3.6）；§1.1 的 37% 属旧语料历史引文，分母不同，不对外并列。

### 2.1 品牌名

- 英文：**PayOnce PDF**（pay once = 一次买断，直击痛点）
- 中文：**一次付费 PDF**
- 备选：`PDFLocal`（SEO 强）、`FlatPDF`（平实）
- 官网域名：`https://payoncepdf.com`（唯一对外域名；DNS / 证书由人工配置）

### 2.2 目标用户

| 用户 | 场景 | 付费动机 |
|---|---|---|
| 律师/法务 | 合同合并、去密、批注、脱敏 | 文件不能上传 |
| 会计/审计 | 发票/报表批量合并、压缩到指定大小 | 批量 + 不上传 |
| HR/行政 | 简历批量转 PDF、签名 | 批量 + 便宜 |
| 学生/研究者 | 论文合并、OCR、拆分 | 便宜、无广告 |
| 小团队 | 统一采购、无账号 | 一次买断 |

**为什么必须做 macOS**：欧美 PDF 重度用户里 Mac 占比高（律所、设计、学术、咨询），
且 Mac 用户对"干净、离线、买断"的工具付费意愿更强。只做 Windows 会直接放弃这块市场。

### 2.3 双平台策略

- **一套代码**：Tauri 2 + Rust，业务逻辑与 UI 完全共享；
- **平台差异隔离**：文件对话框、菜单栏、快捷键、安装包、签名分别适配；
- **同时开发、错峰发布**：M1 起两个平台都能编译；Windows 先发 beta，macOS 紧随其后（≤2 周）；
- **CI 矩阵**：`windows-latest` + `macos-14`（arm64）+ `macos-13`（x64）三路构建。

## 4. 价值主张（按优先级）

1. **不订阅**：一次买断，无月费。
2. **不上传**：文件处理全部本地，文件内容与文件名永不上传；三类运行时请求可枚举、可抓包验证（§22.7 / `site/privacy.html`）。

5. **不冒充全能**：功能面向 PDFgear 桌面版对标补齐，做不好的明确说不支持（§22 修订；原表述「只做高频四件事」已作废）。

## 6. 设计原则

1. **本地优先**：任何**文件处理**功能不得依赖服务器；OCR、转换、压缩、改字、导出全部本机完成。唯一例外是用户主动安装可选 OCR 语言包（下载公开静态字典，不含任何用户数据，见 §22.7）。
2. **无账号**：不收集邮箱、不建用户体系；授权用离线密钥。
3. **默认安全**：不做遥测；日志只在本机，默认关闭。
4. **可验证**：提供"网络活动"说明页与 `site/verify.html`，把三类运行时请求逐条列出，教用户用抓包工具验证文件不上传。
5. **诚实**：做不到的能力写进 FAQ，不夸大。

## 7. 功能需求（含验收标准）

### F1 合并 PDF

- 拖入多个 PDF，可排序、可删除；
- 支持加密 PDF：提示输入密码（仅用于读取，不破解）；
- 输出单文件，保留书签（可选开关）；
- **验收**：100 个文件（合计 500MB）在 4 核机器上 ≤ 60 秒完成；内存峰值 ≤ 1GB；输出页数 = 输入页数之和。

### F2 拆分 PDF

- 三种模式：每 N 页一份 / 指定页码范围 / 按书签层级；
- 输出到指定文件夹，文件名模板可配置（默认 `{原名}_{序号}.pdf`）；
- **验收**：500 页文件按每 10 页拆分，输出 50 个文件，页数与顺序正确。

### F3 压缩到指定大小

- 输入目标大小（如 5MB），自动选择图像降采样与重编码参数；
- 显示"预计大小/实际大小/画质档位"；
- 不改变文字层与书签；
- **验收**：20MB 扫描件压缩到 ≤5MB，文字仍可选中；肉眼无明显模糊（提供前后对比图）。

### F4 图片互转

- PDF → PNG/JPG（可设 DPI：72/150/300）；
- 图片 → PDF（可设页面大小、边距、排序）；
- **验收**：300DPI 导出 10 页 ≤ 30 秒；图片转 PDF 后页序正确。

### F5 本地 OCR

- 引擎：Tesseract（Apache-2.0），内置 `eng` + `chi_sim`；
- 输出：可搜索 PDF（文字层叠加）或 TXT；
- 支持选择页面范围；
- **验收**：10 页清晰扫描件 ≤ 60 秒；英文识别准确率 ≥ 95%（标准测试集）；中文 ≥ 90%。

### F6 签名与表单

- 手写/图片签名，拖放定位，可调整大小；
- 表单字段可填写并"扁平化"（flatten）；
- **验收**：签名后文件在 Adobe Reader 中显示正常；扁平化后字段不可再编辑。

### F7 批量处理

- 选择一个文件夹，应用同一操作（合并/压缩/OCR/转图片）；
- 输出到新文件夹，生成 `report.csv`（文件名、耗时、结果、错误码）；
- **验收**：200 个文件批量压缩不崩溃；失败文件有明确错误码，不中断队列。

### F8 授权与试用

- 7 天全功能试用，无需邮箱；
- 买断密钥：Gumroad 购买后发放 `PAYONCE-XXXX-XXXX-XXXX`；
- 激活：首次联网校验一次，之后离线可用（缓存签名）；
- **验收**：断网可正常使用；试用到期后只限制导出，不删除用户文件。

### F9 自动更新

- 使用 Tauri Updater，签名校验；
- 检查更新可关闭；
- **验收**：旧版本能升级到新版本，失败可回滚。

## 9. 技术方案（建议）

### 9.1 栈

- **桌面框架**：Tauri 2（Rust + React 19 + TypeScript）——与 Grabber 一致，可复用构建/签名/更新经验
- **macOS 目标**：`aarch64-apple-darwin` + `x86_64-apple-darwin`，合并为 universal binary
- **Sidecar 构建**：qpdf / tesseract / tessdata 需同时提供 Windows x64、macOS arm64、macOS x64 三份，
  随包签名（macOS 需 `codesign --deep` 或逐文件签名）
- **PDF 引擎**：PDFium（BSD-3，通过 `pdfium-render` 绑定）
- **结构操作**：qpdf（Apache-2.0）sidecar，用于合并/拆分/线性化
- **图像重编码**：Rust `image` crate（MIT/Apache-2.0）
- **OCR**：Tesseract（Apache-2.0）sidecar + tessdata
- **存储**：SQLite（仅任务历史，可选关闭）
- **授权**：Ed25519 离线签名 + Gumroad 首次校验

### 9.2 许可红线（必须遵守）

| 组件 | 许可 | 可用？ |
|---|---|---|
| PDFium | BSD-3 | ✅ |
| qpdf | Apache-2.0 | ✅ |
| Tesseract | Apache-2.0 | ✅ |
| MuPDF | AGPL-3.0 | ❌ 禁止 |
| Ghostscript | AGPL-3.0 | ❌ 禁止 |
| LibreOffice | MPL-2.0 | ⚠️ 体积大，v1.1 再评估 |

## 10. 数据与隐私

- 不收集任何用户数据；
- **文件内容与文件名永不上传**；任何文件处理功能都不联网；
- 本地日志默认关闭，开启后仅记录操作类型与错误码；
- 运行时网络请求只有三类且可枚举：① 激活只发送密钥与机器指纹哈希（不可逆），不发送文件信息；② 可选更新检查（版本/平台/架构，可关闭）；③ 用户主动安装 OCR 语言包（`https://raw.githubusercontent.com/tesseract-ocr/tessdata_fast/main/<lang>.traineddata`，URL 只含语言代码，不含文件名、路径、机器指纹或任何用户数据）。
- **不得对外宣称「零网络请求」**；抓包验证清单见 `site/verify.html`，三类请求逐一列明。

- 右侧：参数面板，随功能切换（目标大小、DPI、语言、页码范围、查找/替换、表单域定义、书签定义、语言包安装等）。
- 底部：进度条 + 取消 + 打开输出文件夹 + 状态文字。
- 首屏一句话（英文原文，不可改写）：**"Your files never leave this computer."**
- 键盘可完成全部操作（可见 focus、Enter/Space 触发、Esc 取消）；支持 `prefers-contrast: more`。
- **诚实标注**：F14 导出与 F16 文本转 PDF 面板必须写明「只导文字层 / 纯文本排版，不还原版式」；F16 语言包安装面板必须写明这是全产品唯一运行时联网点、请求只含语言代码。

## 22. 范围变更记录（2026-11-16，用户授权）

### 22.1 决策来源

用户原话：

> 「PDFgear 能实现的功能 onecpdf 也应该实现，因为它也是本地处理，并没有另调云上 api，
> 所以我建议功能上直接向它对标，onecpdf 在功能只能比它强不能比它弱，因为它是免费的，
> 如果它不插广告的话，我们的功能如果不比它强的话，用户是不可能选我们的」

以及此前场景锚点：在 Acrobat Reader 里看 PDF 时发现几处要修，不想转 Word、不想订 Acrobat，只想**就地改原 PDF**。

### 22.2 事实核对（纠正前提，见 `docs/pdfgear-parity-matrix.md` §0）

- PDFgear 核心编辑/合并/拆分/压缩/转换确实本地；**但官方承认 AI 与部分移动端任务走服务端**，AI 走 Microsoft Azure OpenAI 且会传输 PDF 内容，需用户显式同意；官方还曾设专节解释压缩/转换为何走服务端，并称正在转向本地。
- 官方明确写「未来可能对 AI 功能、高精度 OCR、复杂 PDF 转换增加付费选项」。
- 因此「文件内容永不上传」「收费确定性」是**我方可以超过它**的维度，不是双方相同的前提。注意措辞：见 §22.7，语言包下载后不能再写「零网络请求」，正确口径是「文件永不上传 + 三类请求可枚举」。

### 22.3 本次批准的范围变化

| 条款 | 原口径 | 新口径 |
|---|---|---|
| §19 第 3 条 | 不做 PDF 深度排版编辑（改文字、重排） | 只禁 WYSIWYG 深度排版编辑器；**就地替换文字与批注解禁** |
| §5.2 | 页面编辑（改文字、换图）整体推到 v1.1+ | 拆出 F10 窄改字，纳入 v1.0 P0 |
| §5.1 | F1–F9 九项 | 增加 F10–F14 五项；**第二轮再增加 F15–F16 两项，共 16 项功能编号 / 15 个 UI 入口** |
| §5.2 | 表单创建/脱敏/书签/打印/邮件列入 v1.1+ | **第二轮移出并实现**（各有诚实边界，见 §22.7） |
| §4 第 5 条 | 「不做全能，只做高频四件事」 | 改为「不冒充全能，功能面对标补齐」 |
| §21 | 「不是更好的 PDF 编辑器」 | 改为「功能对标 + 三条硬承诺」 |
| §16 | 左侧七个功能入口 | 改为 15 个入口，列表可独立滚动 |
| §7 / §14 / §16 | 未涉及新功能验收 | 新功能验收标准见 §22.5 / §22.7 |

**保持不变**：§6 本地优先 / 无账号 / 默认安全 / 可验证 / 诚实；§9.2 许可红线（禁 AGPL）；§8 安装包 ≤100MB；§10 数据与隐私；§19 其余 5 条（云端服务、账号、移动端、DRM 破解、企业 SSO、AI 聊天读 PDF）。

### 22.4 明确**不**因本次变更而放宽的事项

1. **不引入云端 AI**。为了对标而加云端问答，会亲手丢掉「**文件内容永不上传**」这一唯一能超过 PDFgear 的硬承诺。
   （第二轮补注：F16 语言包下载是用户主动下载公开静态字典，URL 只含语言代码、不含任何用户数据，不属于「云端文件处理」，也不改变文件永不上传这一承诺；但「零网络请求」的绝对表述已作废，见 §22.7。）
2. **不引入 AGPL 组件**。Word/Excel 高保真转换需要商业 SDK 或 LibreOffice（体积 ~200MB，超 §8 上限），本次只做文字层导出并在 UI/文档里明说降级。
3. **不做 WYSIWYG 编辑器**。与 §18 支持邮件 ≤0.1 封/单、$39 买断、六周排期的成本结构冲突；§22.8 已用「提价 + 收窄边界」处理该冲突，但 WYSIWYG 编辑器仍需单独立项并单独批准支持预算。
4. **不降低既有安全约束**。新命令全部复用 `execute()`，不改原文件、原子提交、错误码、取消、日志。

### 22.14 F19 字符集边界：英文、科学符号、数学公式（2026-11-21 15:35）

**触发**：用户把「30 日」改成「45 日」成功后追问「还有英文和一些科学符号或数学公式呢，这些能否改？」。这类问题不能靠推理回答，本轮造了 5 页真实样本 `tests/fixtures/text_symbols.pdf`（英文 / Latin-1 符号 / 内嵌 Arial 数学符号 / 上下标 / 分式），逐条跑 F19 并用渲染图目视确认。生成脚本 `scripts/make-symbol-fixture.py`，验证见 `docs/test-report.md` §25。

| 内容类型 | 能否改 | 依据 |
|---|---|---|
| **英文、数字、ASCII 标点** | **能**，最稳 | 走 ASCII 路径，不触发字体闸门；实测 `30`→`45`，同页另一处 `30` 不受影响 |
| **Latin-1 符号** `± ° µ × ÷ · § ¶` | **能**（本轮修） | WinAnsiEncoding 覆盖 U+00A0–U+00FF，内置 Helvetica 也能写。原先「非 ASCII 即要求内嵌字体」一刀切误拒，已改为「未嵌入字体只放行 Latin-1」 |
| **Latin-1 之外数学符号** `≈ ≤ ≥ ∑ ∫ √ π Ω Δ` | **看字体**：PDF 内嵌含该字形的字体就能改，未嵌入则拒绝 | 实测内嵌 Arial 子集：`3.14`→`2.72` 成功，`≈ ≤ ≥ ∑ ∫ √ π Ω` 原样保留且渲染正常 |
| **上下标**（H₂O、x²） | **整段不行为**，**单独框上标可以** | 上下标是「小字号 + 基线偏移」的独立文本对象。整段替换会把新文字压进首个对象、沿用它的大字号，上标被压成正文大小、排版即毁 → 新增**字号一致性闸门**（宽松框高度比 > 1.5 即拒绝）。只框上标本身（同字号）可正常改，实测 `H2O`→`H3O` |
| **分式 / 整条公式** | **不能** | 分子、分母是独立对象，横线是矢量路径而非文字。跨行拖选被「行内垂直中心连续性」拒绝；单个数字/符号可以改，但改不了分式结构 |
| **目标字符在字体子集里不存在** | 拒绝，不写坏文件 | PDFium 缺字形会静默写空格，由写后读回校验拦下：删除输出、原文件字节不变 |

**闸门现状（F19 共五道）**：① `/Rotate != 0` 拒绝；② 文字层顺序 ≠ 内容流顺序拒绝；③ 选区单行连续；④ **选区内字号一致**（§22.14 新增）；⑤ 写后读回校验（新文字可读 + 原文计数 −1）。

**明确不做**：插入公式对象、换字体/字号/颜色、LaTeX 分式结构编辑、Type3 与 Symbol/Dingbats 编码字体、跨行或跨段落替换。

**对外口径**：可写「英文、数字、中文和常见符号（± ° µ × ÷）都能就地改；公式里单独的数字或符号能改，整条公式改不了」。**不得**写「支持公式编辑」「所见即所得」。

**真机状态**：本轮全部证据为引擎级 + 渲染目视，**未在真实窗口人工验证**；真机用例扩到 **69 条**（新增 3 条），`result` 仍全空。

### 22.15 F19 连续编辑：同一份文档改多处（2026-11-21 16:27）

**触发**：用户实测反馈「导入 `text_symbols.pdf` 后测试发现只能修改一次，如果这篇文档有多处修改怎么办」。

**根因**：`runRectEdit` 固定拿 `files[0].path`（永远是用户导入的原始文件）当输入，但第一次改完预览已经切到 `xxx_edited.pdf`。第二次框选的矩形属于结果文件，引擎却去改原件——坐标对不上，`expected` 校验报「预览与引擎不一致」；偶尔对上了，也是**从原件重新开始**，第一处改动被丢掉。所以观感就是「只能改一次」。

| 项 | 决定 |
|---|---|
| 输入 | 改为**当前预览的文件**（`resultFile?.path ?? files[0]?.path`），保证「框选坐标」和「被改文件」是同一份 |
| 输出 | 首次 → `xxx_edited.pdf`；再次 → 仍写回这份文件，**单文件累积**，不产生 `_edited_1 / _edited_2` 一堆副本 |
| 覆盖许可 | 请求新增 `inPlace` 标志。前端只对**本次会话自己生成的产物**置真；后端 `commit_one_chained` 再校验文件名形态（`*_edited` 或 `*_edited_N`），双层把关。用户原件永远不会被写 |
| 预览刷新 | 原地更新时路径不变，靠 `reloadToken` 自增强制重载页数、图像与文字层；且**保留当前页码**，只有真的换文件才回第 1 页 |
| 安全兜底 | 用户拿到的文件本身就叫 `xxx_edited.pdf` 时，它不在会话产物集合里 → 仍另存为 `xxx_edited_edited.pdf`，绝不覆盖 |
| 回到输入 | 点「返回原文件」后再改，会从原件重新开始并另存（旧结果保留，不丢数据） |

**行为**：改第 1 处 → 改第 2 处 → … 全部累积在同一个 `xxx_edited.pdf` 里，原始文件字节始终不变。

**不支持撤销**：每次「直接改这一处」都会立刻覆盖结果文件；需要保留中间版本请自行复制。跨行/跨字号/缺字形等闸门与 §22.13–22.14 完全一致。

**验证**：`e2e_rect_edit_chained_two_rounds`（两轮累积）、`e2e_rect_edit_in_place_updates_same_file`（Windows 上覆盖已被 PDFium 读过的文件）、`chained_commit_*` 3 条、`edited_stem_detection`；`cargo test --lib` **59 PASS / 0 FAIL**。真机用例扩到 **70 条**（新增 `RD-G0-18`）。

### 22.16 真机回归：改完一处后画布仍可继续框选（2026-11-21 17:20）

**触发**：用户实测「改了 Invoice No. 30 → 60 后，鼠标就不能再选框了」。

**根因**：`canSelect` 里有一条 `&& !resultMode`。F18 时代它是对的——结果预览时「填入改字/批注/脱敏」填的是文本查找参数、执行读原文件，放行会「看着结果改原件」。但 F19 按坐标执行，且 §22.15 已把输入改成当前预览文件，这条闸门对 F19 就变成了「第一次改完再也框不动」。

| 项 | 决定 |
|---|---|
| 判定 | `canSelectOnCanvas()` 纯函数：`!resultMode \|\| selectableInResult` |
| 例外范围 | `selectableInResult` 仅对本会话 F19 产出的 `*_edited` 为真；压缩/拆分/合并等输出仍禁框选 |
| 同批更新 | `chainableResultPath` 与 `resultFile` 在同一次批量更新里设置，避免晚一帧先按普通结果处理 |
| 动作条 | 结果预览隐藏「填入改字/批注/脱敏」，只保留「直接改这一处」 |
| 页码 | 切到本次改字结果时保留页码，不再弹回第 1 页 |
| 替换词 | 任务成功后清空「改成」，防止旧词被误用到新选区 |

**验证**：`tests/selection-geometry.test.mjs` 新增 4 条（普通预览 / 非本会话结果 / 本会话结果 / 缺图缺文字层），前端 **28 PASS / 0 FAIL**；`tsc --noEmit` 通过。真机用例 **70 → 71 条**（`RD-G0-19`），`result` 仍全空。

### 22.17 工作台布局改版：三块可收，画布吃满（2026-11-21 19:40）

**触发**：用户截图反馈「整个板面布局非常差，中间的文档编辑页面被挤在上面一小块地方」，要求左右侧栏与中间下半部分改成可收缩、不用时隐藏。

| 项 | 决定 |
|---|---|
| 画布 | `flex: 1 1 auto; height: auto; min-height: 210px`，由剩余空间决定 |
| 左 / 右栏 | 网格列宽用 `--left-w / --right-w` 变量，收起置 0；元素保留槽位（`visibility:hidden` + `overflow:hidden`），**不可用 `display:none`**，否则后面的列会左移错位 |
| 底部文件区 | 拖放区紧凑成一行（44px），与文件列表放进 `.dock`：`flex: 0 0 auto`、`max-height: 52%`、内部滚动；有文件后默认收起 |

| 标语 | 移到顶栏，窄窗口（<1240px）隐藏，不再占工作区一行 |

### 22.18 追补：左右栏拖拽调宽（2026-11-21 20:00，用户「还是不能缩放」）

**触发**：用户复测上一轮改版后反馈「左右两栏还是不能缩放」——22.17 只做了收起/展开，没做拖拽改宽；用户拖面板边缘毫无反应。
